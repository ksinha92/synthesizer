<objective>
## Goal
Implement the workflow bounded context: DAG definition (nodes + edges), validation (cycle detection, node type constraints), execution engine (topological dispatch of node operations via Celery), and workflow CRUD API — so users can chain Discover → Mask → Generate → Subset → Export into automated pipelines.

## Purpose
Workflows turn individual TDM operations into repeatable, schedulable pipelines. Instead of manually running discovery, then masking, then generation separately, a workflow chains them. This is the automation layer that makes DataWrangler operational, not just interactive.

## Output
- Workflow domain: Workflow, WorkflowNode, WorkflowEdge entities
- WorkflowExecutor: validates DAG, dispatches nodes in topological order via Celery
- Workflow API: CRUD + execute + status
- Dual-mode support: JSON DAG definition (frontend visual builder in Phase 16)
</objective>

<context>
## Prior Work — Workflow nodes dispatch to these engines:
- Discovery (Phase 5), Synthetic/Faker (Phase 6), Masking (Phase 13), Subsetting (Phase 14)
</context>

<acceptance_criteria>

## AC-1: Workflow DAG validates structure and detects cycles
```gherkin
Given a workflow definition with nodes and edges
When the DAG is validated
Then cycle detection rejects circular dependencies
And node type validation ensures valid types (discover, mask, generate, subset, export)
And edge validation ensures connections are type-compatible (e.g., discover before mask)
```

## AC-2: Workflow executor dispatches nodes in topological order
```gherkin
Given a valid workflow DAG
When POST /workflows/{id}/execute is called
Then nodes execute in topological order (parents before children)
And each node dispatches its operation via Celery (discovery, masking, etc.)
And per-node status tracks: pending → running → completed/failed
And the workflow job updates progress as nodes complete
```

## AC-3: Workflow CRUD API with JSON DAG definition
```gherkin
Given an authenticated user
When POST /workflows is called with a DAG definition (nodes + edges as JSON)
Then the workflow is created and persisted
And GET /workflows lists workflows with status and last run info
And POST /workflows/{id}/execute dispatches execution (202 async)
And the DAG definition is stored as JSONB for frontend visual builder consumption
```

    1. Create domain/workflow/entities.py (NO framework imports):
       - Workflow(AggregateRoot): project_id, name, description, dag_definition (dict — {nodes: [], edges: []}), schedule (str|None — cron), is_active (bool)
       - WorkflowNode: id (str), type (discover|mask|generate|subset|export), config (dict), position (dict — {x, y} for visual builder)
       - WorkflowEdge: source_node_id, target_node_id

    2. Create domain/workflow/services.py (NO framework imports):
       - WorkflowValidator:
         - validate_dag(dag) -> list[str] errors: cycle detection, valid node types, edge compatibility
         - get_execution_order(dag) -> list[str] node_ids: topological sort
       - Node type compatibility rules:
         - discover → mask, generate, subset (discovery must come first)
         - mask → export (masking produces output)
         - generate → export (generation produces output)
         - subset → mask, export (subset can be masked or exported)

    3. Create domain/workflow/events.py:
       - WorkflowStepCompleted(DomainEvent): workflow_id, node_id, node_type, status
       - WorkflowCompleted(DomainEvent): workflow_id, node_count, duration_ms

    4. Create infrastructure/messaging/workflow_tasks.py:
       - run_workflow_task(workflow_id, project_id, job_id):
         - Load workflow + validate DAG
         - Get execution order (topological sort)
         - For each node in order:
           - Dispatch the appropriate operation (discovery/masking/generation/subsetting)
           - Wait for completion: poll job status every 5 seconds, per-node timeout 30 minutes, overall workflow timeout 2 hours <!-- audit-added: polling interval + timeouts -->
           - Update per-node status
           - If node fails: mark workflow as failed, stop execution
           - If timeout: mark node as failed with "timeout" error
         - Update workflow job to completed
         - 1 retry, 120s backoff (workflow failures are usually node-specific)

    Avoid: Parallel node execution for MVP — sequential topological order is simpler and sufficient.
  </action>
  <verify>

    - Topological sort produces correct execution order
    - Domain has zero framework imports
