<objective>
## Goal
Harden the platform for production: connection pooling, structured error responses, request correlation IDs, enhanced health checks, Redis pub/sub for SSE, and production Docker Compose finalization.

## Purpose
The difference between "works in dev" and "works in production" — pooling prevents connection exhaustion, correlation IDs enable distributed tracing, standardized errors help frontend handle failures consistently.

## Output
- Connection pool tuning for connectors
- Request correlation ID middleware (X-Request-ID)
- Standardized error response format across all endpoints
- Enhanced health checks with dependency verification
- Production Docker Compose finalization
</objective>

<acceptance_criteria>

## AC-1: Request correlation IDs on every response
```gherkin
Given any API request
When the response is returned
Then X-Request-ID header is present (generated or forwarded from request)
And structlog includes request_id in every log entry for that request
```

## AC-2: Standardized error responses
```gherkin
Given any API error (400, 401, 403, 404, 500)
When the error response is returned
Then it follows: {"error": "error_code", "detail": "message", "request_id": "uuid"}
And 500 errors do NOT expose stack traces to the client
```

## AC-3: Production Docker Compose is deployment-ready
```gherkin
Given docker-compose.prod.yml
When deployed
Then all services have resource limits, restart policies, health checks
And no database/redis ports are exposed externally
And Nginx handles SSL termination + proxy
And frontend service is added (was missing from Phase 10 prod compose)
```

</acceptance_criteria>
