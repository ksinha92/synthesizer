<objective>
## Goal
Implement graph-aware data subsetting: build FK dependency graph from discovered relationships, traverse upstream/downstream from root tables, apply WHERE filters, dry-run analysis, and execute subset extraction via Celery.

## Purpose
Subsetting is critical for creating right-sized test environments. Instead of full database copies (terabytes), teams get referentially-intact subsets (gigabytes → megabytes). The graph-aware traversal ensures FK integrity — no orphaned rows.

## Output
- Subsetting bounded context: SubsetConfig, DependencyGraph entities
- SubsettingEngine: graph builder, upstream/downstream traversal, WHERE filter, dry-run analysis
- Subset API: configs, analyze (dry-run), execute (async)
</objective>

<acceptance_criteria>

## AC-1: FK dependency graph built from discovered relationships
```gherkin
Given discovered relationships for a schema
When SubsettingEngine.build_graph(relationships) is called
Then a directed graph is built: nodes = tables, edges = FK dependencies
And upstream traversal from a table returns all parent tables (recursively)
And downstream traversal returns all child tables (recursively)
And cycles are detected and handled (break at cycle point)
```

## AC-2: Dry-run analysis shows row counts per table
```gherkin
Given a subset config with root table, traversal direction, and WHERE filter
When POST /subset/analyze (dry-run) is called
Then it returns per-table row counts: {table_name, full_count, subset_count, percentage}
And the total row count across all tables
And no data is actually extracted (read-only analysis)
```

## AC-3: Subset execution extracts referentially-intact data
```gherkin
Given an approved subset config
When POST /subset/execute is called
Then a Celery job extracts data in traversal order (parents before children for upstream)
And FK references are satisfied (no orphaned rows)
And the result is stored via storage backend
And job progress updates per table
```

       - SubsetConfig(AggregateRoot): project_id, name, source_connection_id, target_connection_id (optional), target_percentage (float), target_row_count (int|None), root_tables (list[dict] — [{table_name, where_filter}]), traversal_strategy ("upstream"|"downstream"|"both")
       - DependencyGraph: nodes (set[str]), edges (dict[str, set[str]]), built from relationships

    2. Create domain/subsetting/events.py:
       - SubsetCompleted(DomainEvent): config_id, table_count, total_rows

    3. Create infrastructure/engine/subsetting_engine.py:
       - SubsettingEngine class:
         - build_graph(relationships: list[dict]) -> DependencyGraph:
           - Create directed graph from FK relationships
           - Detect cycles (DFS with visited/recursion stack)
           - Return graph with cycle_tables flagged

         - get_traversal_tables(graph, root_tables, direction) -> list[str]:
           - "upstream": BFS from root following FK edges to parents (child→parent)
           - "downstream": BFS from root following reverse edges to children (parent→child)
           - "both": union of upstream + downstream
           - Return in topological order (parents first)

         - analyze_dry_run(connector, graph, config) -> list[dict]:
           - For each table in traversal:
             - Full count: SELECT COUNT(*) FROM table
             - Subset count: estimate based on target_percentage or target_row_count
               - Root table: apply WHERE filter, count matching rows
               - Related tables: estimate based on FK cardinality ratio
             - Return [{table_name, full_count, subset_count, percentage}]
           - Total row count across all tables
           - NO data extraction — read-only

         - execute_subset(connector, graph, config) -> dict[str, int]:
           - Extract data table by table in traversal order
           - Root table: validate WHERE filter before use — reject semicolons and DDL keywords (DROP, ALTER, DELETE, INSERT, UPDATE, TRUNCATE, GRANT, REVOKE). Log rejected filters. Only allow SELECT-safe expressions. <!-- audit-added: SQL injection prevention -->
             SELECT * WHERE {validated_filter} LIMIT {target}
           - Parent tables: SELECT * WHERE id IN (...) — chunk IN clauses into batches of 1000 IDs to avoid query size limits <!-- audit-added -->
           - Child tables: SELECT * WHERE fk_col IN (...) — same 1000-ID chunking
           - Store results via storage backend
           - Return {table_name: row_count}

    Avoid: Loading all table data into memory — stream chunks.
    Avoid: N+1 queries for FK resolution — batch IN clauses.
  </action>
