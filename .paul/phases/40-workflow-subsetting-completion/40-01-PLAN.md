<objective>
Complete the workflow, subsetting, and masking frontends by wiring execution history, config listing, cron scheduling, and rule management to backend endpoints built in Phase 38.
</objective>

<acceptance_criteria>
## AC-1: Workflow Execution History + Cron Schedule
Given the workflow detail page, when a workflow is loaded:
- An "Execution History" section shows below the DAG canvas listing past executions from GET /workflows/{id}/executions (built in Phase 38)
- Each entry shows: status badge, progress %, started_at, completed_at, error (if failed)
- Empty state when no executions exist

Given the workflow create/edit flow:
- A "Schedule" input field accepts an optional cron expression (e.g. "0 2 * * *")
- The value is sent as the `schedule` field in the POST/PUT body
- Existing schedule displays on the workflow detail page

Store changes:
- Add `fetchExecutions(projectId, workflowId)` → GET /workflows/{id}/executions
- Add `executions` state array

## AC-2: Subset Config Listing
Given the subsetting page, when user navigates to it:
- A "Saved Configs" section lists existing subset configs from GET /subset/configs (built in Phase 38)
- Each entry shows: name, target %, traversal strategy, created date
- Clicking a config loads it for analysis (calls analyze with that config_id)
- Empty state when no configs exist

Store changes:
- Add `fetchConfigs(projectId)` → GET /projects/{projectId}/subset/configs
- Add `configs` state array

## AC-3: Masking Rule Edit + Delete
Given a masking policy's rules:
- Each rule displays an "Edit" button opening an inline editor for masking_type, masking_config, preserve_format, deterministic
- Each rule displays a "Delete" button with confirmation
- Edit calls PUT /masking/policies/{id}/rules/{id} (built in Phase 38)
- Delete calls DELETE /masking/policies/{id}/rules/{id} (built in Phase 38)

Store changes:
- Add `updateRule(projectId, policyId, ruleId, data)` → PUT
- Add `deleteRule(projectId, policyId, ruleId)` → DELETE
</acceptance_criteria>
